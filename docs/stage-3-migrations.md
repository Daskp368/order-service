# Этап 3. Миграции базы данных

## Результат

Структурой базы данных управляет Flyway. При запуске приложения первая миграция создаёт таблицы `users` и `orders`, ограничения и индексы. Hibernate не создаёт и не изменяет таблицы.

## Зачем нужны миграции

Миграция — это зафиксированное изменение структуры или данных базы. Она позволяет получить одинаковую схему на компьютере разработчика, в тестовой среде и на сервере.

Файл первой миграции:

```text
src/main/resources/db/migration/V1__create_users_and_orders.sql
                                │ │
                                │ └── описание
                                └──── версия и два подчёркивания
```

После успешного выполнения Flyway записывает миграцию в `flyway_schema_history`. При следующих запусках он сравнивает найденные файлы с этой таблицей и выполняет только новые версии.

У каждой применённой миграции хранится контрольная сумма. Поэтому уже применённый файл `V1` нельзя редактировать: изменение будет обнаружено при проверке. Следующее изменение схемы оформляется новым файлом, например `V2__add_delivery_address.sql`.

## Зависимости

- `flyway-core` — основная логика поиска, проверки и выполнения миграций;
- `flyway-database-postgresql` — поддержка PostgreSQL;
- `postgresql` — JDBC-драйвер, через который Flyway подключается к базе.

Версии этих библиотек согласованы и управляются Spring Boot, поэтому в отдельных зависимостях версии не указаны.

## Автоконфигурация Spring Boot

Отдельный Java-класс для запуска миграций не нужен. Spring Boot видит Flyway в classpath, берёт уже настроенный `DataSource` и вызывает миграции во время запуска приложения до создания JPA `EntityManagerFactory`.

Настройки:

```properties
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
spring.jpa.hibernate.ddl-auto=validate
```

- `spring.flyway.enabled=true` разрешает автозапуск Flyway;
- `spring.flyway.locations` указывает папку с миграциями;
- `validate` разрешает Hibernate только проверять соответствие Java-сущностей схеме, но не изменять её.

Первые две настройки совпадают со значениями Spring Boot по умолчанию. В учебном проекте они записаны явно, чтобы поведение было видно в конфигурации.

На этом этапе Entity-классов ещё нет, поэтому Hibernate пока нечего сопоставлять с таблицами. Полноценная проверка `validate` начнёт работать после создания сущностей на следующем этапе.

## Таблица `users`

| Столбец | Назначение |
|---|---|
| `id UUID PRIMARY KEY` | Уникальный идентификатор пользователя |
| `username VARCHAR(50)` | Нормализованное уникальное имя |
| `password_hash VARCHAR(60)` | BCrypt-хеш, а не исходный пароль |
| `role VARCHAR(20)` | Роль `USER` или `ADMIN` |

Ограничения `CHECK` дополнительно проверяют длину и формат username, длину BCrypt-хеша и допустимую роль.

## Таблица `orders`

| Столбец | Назначение |
|---|---|
| `id UUID PRIMARY KEY` | Уникальный идентификатор заказа |
| `user_id UUID` | Идентификатор владельца |
| `description VARCHAR(1000)` | Описание заказа |
| `status VARCHAR(20)` | Состояние заказа |
| `created_at TIMESTAMP` | Дата и время создания |

`FOREIGN KEY` гарантирует, что заказ не может ссылаться на отсутствующего пользователя. `ON DELETE CASCADE` удаляет заказы вместе с владельцем.

Ограничение статуса разрешает только `CREATED`, `IN_PROGRESS` и `COMPLETED`. Проверка описания запрещает пустую строку и строку только из пробелов.

## Индексы

```sql
CREATE INDEX idx_orders_user_id ON orders (user_id);
CREATE INDEX idx_orders_created_at ON orders (created_at DESC);
```

Первый индекс ускоряет получение заказов конкретного пользователя. Второй помогает сортировать заказы от новых к старым. Индекс ускоряет чтение, но занимает место и немного замедляет запись, потому что его тоже необходимо обновлять.

## Важные термины

- DDL — команды изменения структуры: `CREATE`, `ALTER`, `DROP`;
- первичный ключ (`PRIMARY KEY`) — уникально определяет строку;
- внешний ключ (`FOREIGN KEY`) — обеспечивает связь между таблицами;
- `UNIQUE` — запрещает повторяющиеся значения;
- `NOT NULL` — запрещает отсутствие значения;
- `CHECK` — проверяет логическое условие;
- индекс — вспомогательная структура для ускорения поиска и сортировки.

## Правило следующих этапов

Применённые миграции не переписываем. Любое следующее изменение структуры базы создаём новой версией миграции.
