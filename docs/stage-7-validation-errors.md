# Этап 7. Валидация и обработка ошибок

## Результат

Ошибки REST API теперь преобразуются в единообразный и понятный JSON. Клиент получает HTTP-статус, безопасное сообщение, путь запроса и время ошибки. Ошибка Bean Validation дополнительно содержит список нарушенных полей.

Этап различает следующие ситуации:

| Ситуация | HTTP-статус |
|---|---:|
| DTO не прошёл Bean Validation | `400 Bad Request` |
| JSON невозможно прочитать | `400 Bad Request` |
| Username уже занят | `409 Conflict` |
| Доменный объект не найден | `404 Not Found` |
| Неожиданная внутренняя ошибка | `500 Internal Server Error` |

Обработка `401 Unauthorized` и `403 Forbidden`, возникающих в цепочке Spring Security до контроллера, будет подключена к тому же формату на этапе JWT.

## Обычная ошибка

Для ошибок создан DTO `ApiErrorResponse`:

```json
{
  "timestamp": "2026-09-08T15:37:42.477Z",
  "status": 409,
  "error": "Conflict",
  "message": "Username уже занят",
  "path": "/api/auth/register"
}
```

Поля имеют следующее назначение:

- `timestamp` — момент формирования ответа в формате ISO-8601;
- `status` — числовой HTTP-статус;
- `error` — стандартное название статуса;
- `message` — безопасное пояснение для клиента;
- `path` — URI запроса без query-параметров;
- `fieldErrors` — ошибки отдельных полей, присутствуют только при валидации DTO.

`timestamp` хранится в DTO как `Instant`, а аннотация `@JsonFormat(shape = JsonFormat.Shape.STRING)` закрепляет его строковое представление. Благодаря этому Java-код остаётся типобезопасным, а формат JSON не зависит от глобальной настройки сериализации дат.

Аннотация:

```java
@JsonInclude(JsonInclude.Include.NON_EMPTY)
```

сообщает Jackson не добавлять `fieldErrors` в JSON, если список пуст. Без неё обычная ошибка содержала бы лишнее поле:

```json
"fieldErrors": []
```

## Ошибка Bean Validation

Если регистрационный DTO нарушает ограничения, ответ выглядит так:

```json
{
  "timestamp": "2026-09-08T15:37:42.477Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Ошибка валидации",
  "path": "/api/auth/register",
  "fieldErrors": [
    {
      "field": "password",
      "message": "Пароль должен содержать не менее 8 Unicode-символов"
    }
  ]
}
```

Каждый элемент списка представлен классом `FieldValidationError`. В ответ попадают только имя поля и сообщение ограничения. Значение, которое прислал клиент, намеренно не возвращается. Благодаря этому исходный пароль не раскрывается в ответе.

Ошибки сортируются по имени поля и сообщению. Это делает JSON и тесты предсказуемыми, даже если Bean Validation вернёт нарушения в другом порядке.

## Путь ошибки валидации

```text
POST /api/auth/register
          ↓
Jackson читает JSON и создаёт RegisterRequest
          ↓
@Valid запускает Bean Validation
          ↓
одно из ограничений нарушено
          ↓
MethodArgumentNotValidException
          ↓
ApiExceptionHandler
          ↓
ApiErrorResponse + HTTP 400
```

Метод `AuthController.register()` и `AuthService.register()` при этом не выполняются. Проверка останавливает запрос на границе приложения.

## `@RestControllerAdvice`

Класс `ApiExceptionHandler` отмечен:

```java
@RestControllerAdvice
```

Spring находит такой класс при создании контекста и применяет его ко всем REST-контроллерам. Это позволяет не писать одинаковый `try/catch` в каждом методе контроллера.

Методы обработчика отмечаются:

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
```

Когда во время обработки HTTP-запроса возникает указанное исключение, Spring MVC вызывает соответствующий метод advice вместо стандартной обработки ошибки.

Если убрать `@RestControllerAdvice`, класс останется обычным Java-классом и Spring MVC не узнает о его обработчиках. Если убрать `@ExceptionHandler`, Spring не будет знать, для какого исключения предназначен метод.

## Ошибка конфликта

`AuthService` по-прежнему выбрасывает `UsernameAlreadyExistsException`, когда нормализованный username уже занят.

На предыдущем этапе статус задавала аннотация `@ResponseStatus`. Теперь она удалена: один глобальный обработчик одновременно выбирает `409 Conflict` и создаёт согласованное тело ответа.

Путь конфликта:

```text
AuthService
    ↓
UsernameAlreadyExistsException
    ↓
ApiExceptionHandler.handleUsernameAlreadyExists(...)
    ↓
ApiErrorResponse + HTTP 409
```

Это работает и для ранней проверки `existsByUsername()`, и для конфликта уникального ограничения PostgreSQL при двух одновременных регистрациях.

## Ошибка отсутствующего ресурса

Создано доменное исключение `ResourceNotFoundException`. Сейчас production-endpoint, которому оно требуется, ещё отсутствует: операции с пользователями и заказами появятся на следующих этапах.

Когда будущий сервис не найдёт объект, он сможет сообщить об этом без зависимости от HTTP:

```java
throw new ResourceNotFoundException("Заказ не найден");
```

Сервис выражает бизнес-результат исключением, а `ApiExceptionHandler` преобразует его в `404 Not Found`. Поэтому сервисному слою не требуется возвращать `ResponseEntity` или знать о контроллере.

Поведение `404` проверено через тестовый контроллер, существующий только внутри теста. Фиктивный endpoint в production-код не добавлялся.

## Некорректный JSON

Есть разница между двумя ошибками:

1. JSON корректен, но данные нарушают правила DTO — возникает `MethodArgumentNotValidException`.
2. JSON оборван или синтаксически неверен — Jackson не может создать DTO, возникает `HttpMessageNotReadableException`.

Во втором случае `@Valid` ещё не запускается. Обработчик возвращает `400 Bad Request` с сообщением `Некорректный JSON`, но без `fieldErrors`, потому что корректного Java-объекта и его полей ещё нет.

## Неожиданная ошибка

Последний обработчик принимает `Exception`. Он является защитной границей для непредвиденных ошибок контроллеров и сервисов.

Клиент получает только:

```json
{
  "status": 500,
  "error": "Internal Server Error",
  "message": "Внутренняя ошибка сервера"
}
```

Исходное сообщение исключения и stack trace в HTTP-ответ не попадают. Сама ошибка записывается в серверный лог, чтобы разработчик мог найти причину.

Перед превращением исключения в `500` обработчик проверяет интерфейс Spring `ErrorResponse`. Если Spring MVC уже определил известный статус, например `405 Method Not Allowed`, этот статус сохраняется.

## Валидация описания заказа

На этапе 7 добавлен только входной DTO `CreateOrderRequest`. Контроллер, сервис и создание заказа пока не реализуются.

Поле `description` имеет два ограничения:

```java
@NotBlank(message = "Описание заказа обязательно")
@TrimmedSize(min = 1, max = 1000, message = "...")
```

`@NotBlank` отклоняет `null`, пустую строку и строку из одних пробелов.

Пользовательская аннотация `@TrimmedSize` проверяет длину после `String.strip()`. Валидатор считает Unicode code points, поэтому один emoji считается одним символом, хотя внутри Java он может занимать два UTF-16 code units.

Валидатор возвращает `true` для `null`. Проверка наличия значения принадлежит `@NotBlank`; каждая аннотация отвечает за одно правило.

При реализации создания заказа сервис удалит пробелы по краям перед сохранением. На текущем этапе проверяется только DTO и не создаётся преждевременная бизнес-операция.

## Тесты

`AuthRegistrationIntegrationTest` проверяет настоящий путь запроса через Security, Controller, Bean Validation, Service, Repository и PostgreSQL:

- JSON ошибки валидации;
- отсутствие отклонённого пароля в ответе;
- единый `409 Conflict` для занятого username;
- `400 Bad Request` для синтаксически неверного JSON;
- прежние позитивные и негативные сценарии регистрации.

`ApiExceptionHandlerTest` использует standalone `MockMvc`. Он проверяет обработчик без запуска базы данных:

- `404 Not Found`;
- безопасный `500 Internal Server Error`;
- сохранение известного статуса `405 Method Not Allowed`.

`CreateOrderRequestValidationTest` напрямую запускает Bean Validation и проверяет:

- строку ровно из 1000 Unicode-символов;
- строку только из пробелов;
- превышение границы 1000 символов.

Полная проверка проекта:

```bash
./mvnw test
```

## Граница этапа

На этапе 7 не добавлялись:

- вход по username и паролю;
- выпуск или проверка JWT;
- `SecurityFilterChain` для Bearer-токена;
- production-endpoints заказов;
- обработка `401` и `403` внутри security-фильтров.

Эти задачи относятся к следующим этапам. Созданная модель `ApiErrorResponse` будет повторно использована для их ответов.
