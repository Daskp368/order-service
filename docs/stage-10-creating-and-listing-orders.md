# Этап 10. Создание и получение заказов

## Результат

Реализованы два защищённых endpoint:

```http
POST /api/orders
GET /api/orders
Authorization: Bearer <token>
```

Пользователь создаёт заказ от своего имени и получает только собственные заказы. Владелец, начальный статус и время создания определяются сервером, а не содержимым клиентского JSON.

## Создание заказа

Запрос:

```http
POST /api/orders
Authorization: Bearer eyJ...
Content-Type: application/json
```

```json
{
  "description": "Новый заказ"
}
```

Успешный ответ:

```http
HTTP/1.1 201 Created
Content-Type: application/json
```

```json
{
  "id": "2715fc32-0bc4-435d-ad2d-d09a7f19c607",
  "userId": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
  "description": "Новый заказ",
  "status": "CREATED",
  "createdAt": "2026-09-11T15:30:00"
}
```

`CreateOrderRequest` содержит только `description`. Даже если клиент добавит в JSON `userId`, `status` или `createdAt`, эти значения не участвуют в создании доменного объекта.

Сервис самостоятельно:

1. Находит текущего пользователя по подтверждённому username.
2. Удаляет пробелы по краям описания методом `strip()`.
3. Назначает найденного пользователя владельцем.
4. Устанавливает `OrderStatus.CREATED`.
5. Устанавливает текущее серверное время.
6. Сохраняет `Order` и преобразует его в `OrderResponse`.

Так клиент не может создать заказ от имени другого пользователя или сразу отметить его выполненным.

## Путь запроса на создание

```text
POST /api/orders + Bearer JWT + JSON
          ↓
JwtAuthenticationFilter проверяет токен и заполняет SecurityContext
          ↓
OrderController получает CreateOrderRequest и Authentication
          ↓
Bean Validation проверяет description
          ↓
OrderService.createOrder(authentication.getName(), request)
          ↓
UserRepository.findByUsername(username)
          ↓
создаётся Order: владелец + очищенное описание + CREATED + время сервера
          ↓
OrderRepository.save(order)
          ↓
OrderResponse → 201 Created
```

Если DTO не проходит проверку, Spring MVC не вызывает метод контроллера: `ApiExceptionHandler` возвращает единый `400 Bad Request`.

## Получение своих заказов

Запрос:

```http
GET /api/orders
Authorization: Bearer eyJ...
```

Ответ этапа 10 — JSON-массив:

```json
[
  {
    "id": "2715fc32-0bc4-435d-ad2d-d09a7f19c607",
    "userId": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
    "description": "Новый заказ",
    "status": "CREATED",
    "createdAt": "2026-09-11T15:30:00"
  }
]
```

Список строится запросом:

```java
findAllByUser_IdOrderByCreatedAtDesc(currentUser.getId())
```

Условие по `user_id` выполняется в PostgreSQL. Сервис не загружает все заказы с последующей фильтрацией в Java. Сортировка `createdAt DESC` также выполняется базой: новые заказы находятся в начале списка.

Даже для `ADMIN` этот endpoint возвращает только его собственные заказы. Общий список `/api/orders/all` и проверка административной роли относятся к этапу 11.

## Почему сервер снова ищет пользователя

JWT хранит username в claim `sub`, а не доменную сущность и не UUID. `Authentication.getName()` сообщает сервису подтверждённое имя, после чего `UserRepository` получает актуальную сущность `User` из базы.

Это разделяет ответственность:

- Spring Security подтверждает личность;
- PostgreSQL хранит актуального доменного пользователя;
- `OrderService` устанавливает владельца бизнес-объекта;
- DTO определяет разрешённые входные и выходные поля.

`userId` из query-параметра или JSON не используется как источник личности.

## DTO вместо Entity

`OrderResponse` содержит ровно пять полей API: `id`, `userId`, `description`, `status` и `createdAt`.

Если вернуть `Order` напрямую, Jackson встретит поле `user`, связанное через `@ManyToOne(fetch = LAZY)`. Это связывает HTTP-формат с внутренней JPA-моделью, может вызвать лишнюю загрузку пользователя и создаёт риск раскрытия его полей, включая хеш пароля.

Ручное преобразование делает границу явной:

```text
Order Entity → OrderResponse → JSON
```

## Транзакционные границы

### `@Transactional`

Метод создания выполняет связанную бизнес-операцию: ищет владельца, создаёт `Order` и сохраняет его. Аннотация открывает транзакцию до входа в метод и завершает её после успешного возврата.

Если внутри метода возникает непроверяемое исключение, Spring откатывает транзакцию. Без транзакционной границы отдельные обращения к репозиториям не образовывали бы одну явно обозначенную бизнес-операцию.

### `@Transactional(readOnly = true)`

Метод списка только читает пользователя и заказы. `readOnly = true` выражает это намерение и удерживает persistence context открытым во время преобразования Entity в DTO.

Аннотации обрабатывает транзакционный proxy Spring. Вызов репозитория сам по себе не объясняет границу всей сервисной операции.

## Аннотации контроллера

### `@RestController`

Регистрирует класс как Spring MVC controller и включает запись возвращаемых Java-объектов в JSON-тело ответа.

### `@RequestMapping("/api/orders")`

Задаёт общий путь класса. Без него методы пришлось бы привязывать к полному пути по отдельности.

### `@PostMapping` и `@GetMapping`

Связывают методы с HTTP-методами `POST` и `GET` по общему пути `/api/orders`.

### `@Valid @RequestBody`

`@RequestBody` просит Jackson создать `CreateOrderRequest` из JSON. `@Valid` запускает Bean Validation до вызова метода контроллера.

### Аргумент `Authentication`

Spring MVC получает его из `SecurityContext`, который заполнил JWT-фильтр. Это не часть пользовательского JSON.

## Тесты

`OrderApiIntegrationTest` проверяет:

- создание заказа с владельцем из JWT;
- игнорирование переданных клиентом `userId`, `status` и `createdAt`;
- очистку крайних пробелов описания;
- начальный статус `CREATED` и серверное время;
- безопасный ответ ровно из пяти полей;
- выборку только заказов текущего пользователя;
- сортировку от новых заказов к старым;
- отдельное поведение собственного списка для `ADMIN`;
- `400 Bad Request` для пустого описания без сохранения заказа;
- `401 Unauthorized` для обоих endpoint без JWT.

Проверка после реализации:

- целевой запуск `./mvnw -Dtest=OrderApiIntegrationTest test` — 5 тестов, 0 ошибок;
- полный запуск `./mvnw test` — 43 теста, 0 ошибок.

## Граница этапа

На этапе 10 не добавлялись:

- `GET /api/orders/all`;
- изменение статуса заказа;
- удаление заказа;
- ролевые правила административных endpoint;
- пагинация;
- `GET /api/orders/{id}`;
- Swagger и Docker.

Пагинация и итоговый объект с `content`, `page`, `size`, `totalElements` и `totalPages` появятся на этапе 13. До этого учебный endpoint возвращает обычный список.

## Контрольные вопросы

1. Почему `CreateOrderRequest` не содержит `userId`, `status` и `createdAt`?
2. Откуда `OrderController` получает текущую `Authentication`?
3. Зачем `OrderService` загружает `User`, если username уже находился в JWT?

5. Как `findAllByUser_IdOrderByCreatedAtDesc` одновременно ограничивает владельца и задаёт порядок?
6. Почему нельзя вернуть JPA-сущность `Order` напрямую?
7. Что обозначает граница `@Transactional` вокруг создания заказа?
8. Почему `ADMIN` через `GET /api/orders` пока видит только собственные заказы?
9. Чем ответ этапа 10 будет отличаться от пагинированного ответа этапа 13?
