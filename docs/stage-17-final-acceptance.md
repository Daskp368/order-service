## Что такое финальная приёмка

Unit-тест отвечает на узкий вопрос о поведении одного класса. Интеграционный тест проверяет совместную
работу нескольких слоёв. Финальная приёмка отвечает на более широкий вопрос: может ли пользователь получить
требуемый результат в реально запущенном приложении, собранном и развёрнутом заявленным способом.

В этом проекте доказательство состоит из трёх частей:

1. Автоматические тесты подтверждают правила отдельных компонентов и их интеграцию.
2. Чистый Docker-запуск подтверждает сборку, конфигурацию, сеть, PostgreSQL и миграции.
3. Сквозные HTTP-запросы подтверждают поведение сервиса с точки зрения клиента.

Успех только одной части недостаточен. Например, зелёные unit-тесты не доказывают, что контейнер может
подключиться к базе, а открытый Swagger UI не доказывает правильную проверку владельца заказа.

## Дополнительные проверки содержимого ответов

Одного HTTP-статуса недостаточно. В успешных ответах дополнительно подтверждено:

- регистрация всегда возвращает роль `USER`;
- вход возвращает `token`, `tokenType: Bearer` и `expiresIn: 1800`;
- `/api/auth/me` возвращает владельца предъявленного JWT;
- заказ получает владельца, `CREATED` и `createdAt` на сервере;
- крайние пробелы описания удаляются;
- страница содержит `content`, `page`, `size`, `totalElements` и `totalPages`;
- в пользовательском списке находятся только заказы владельца JWT;
- изменение статуса не меняет владельца и описание;
- список пользователей не содержит пароль или BCrypt-хеш;
- удаление пользователя делает его старый JWT непригодным;
- `ON DELETE CASCADE` удаляет оставшиеся заказы пользователя.

## Путь запроса регистрации

```text
HTTP POST /api/auth/register
    ↓
SecurityFilterChain разрешает публичный endpoint
    ↓
AuthController.register
    ↓ @Valid
RegisterRequest проходит Bean Validation
    ↓
AuthService.register
    ├─ нормализует username
    ├─ проверяет уникальность
    ├─ создаёт BCrypt-хеш
    └─ назначает Role.USER
    ↓ @Transactional
UserRepository.saveAndFlush
    ↓
Hibernate формирует INSERT
    ↓
PostgreSQL проверяет NOT NULL и UNIQUE
    ↓
UserResponse без passwordHash
    ↓
HTTP 201 Created
```

`@Valid` запускает проверку входного DTO. `@Transactional` задаёт границу операции с базой. Контроллер не
хеширует пароль и не работает с репозиторием напрямую: это ответственность сервиса.

## Путь защищённого запроса

```text
Authorization: Bearer <jwt>
    ↓
JwtAuthenticationFilter
    ├─ извлекает токен
    ├─ проверяет подпись и срок действия
    └─ получает username
    ↓
DatabaseUserDetailsService читает пользователя и актуальную роль из PostgreSQL
    ↓
Authentication сохраняется в SecurityContext
    ↓
SecurityFilterChain проверяет требуемую роль
    ↓
Controller получает Authentication
    ↓
Service применяет бизнес-правила владельца
    ↓
Repository → PostgreSQL
    ↓
DTO → JSON → HTTP-ответ
```

Проверка токена и проверка прав — разные задачи. Валидный JWT доказывает аутентификацию, но не даёт обычному
пользователю права вызвать ADMIN endpoint. Поэтому неверный или отсутствующий JWT приводит к `401`, а
валидный JWT с недостаточной ролью — к `403`.

## Почему роль читается из базы

JWT содержит username, но актуальный пользователь загружается из PostgreSQL при каждом защищённом запросе.
Это даёт два важных свойства:

1. Удалённый пользователь сразу теряет доступ, даже если срок его JWT ещё не закончился.
2. Решение об авторизации использует актуальную роль из базы.

Финальный сценарий подтвердил первое свойство: после удаления `USER` его ранее рабочий токен получил `401`.
