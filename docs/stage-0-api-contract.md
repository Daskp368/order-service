# Этап 0. Требования и API-контракт

Статус: утверждён 3 сентября 2026 года.

Этот документ хранится вместе с проектом и фиксирует поведение микросервиса до начала написания Java-кода. Если во время разработки возникнет неоднозначность, сначала сверяемся с этим контрактом, а не добавляем поведение по предположению.

## 1. Цель сервиса

Микросервис управляет пользователями и заказами. Пользователь регистрируется, входит в систему, создаёт заказы и работает только со своими заказами. Администратор управляет всеми пользователями и заказами.

## 2. Технические решения

| Область | Решение |
|---|---|
| Java | Java 17 |
| Фреймворк | Spring Boot 3 |
| Сборка | Maven |
| База данных | PostgreSQL 15 |
| Миграции | Flyway |
| Аутентификация | Spring Security и JWT |
| Документация API | Swagger / OpenAPI |
| Контейнеризация | Docker и Docker Compose |
| Внедрение зависимостей | Через конструктор |
| Lombok | Не использовать на первых этапах |
| Entity/DTO-маппинг | Выполнять вручную для обучения |

## 3. Роли и общие правила доступа

Роли:

- `USER` — обычный пользователь;
- `ADMIN` — администратор.

Общие правила:

1. При обычной регистрации всегда назначается роль `USER`.
2. Клиент не может передать роль при регистрации.
3. Все операции с заказами требуют JWT.
4. Пользователь не передаёт свой `userId` при создании или получении заказов: сервер определяет пользователя из Spring Security.
5. `USER` видит только собственные заказы.
6. `ADMIN` может получить список всех заказов.
7. `USER` не может изменять заказ.
8. Статус заказа может изменять только `ADMIN`.
9. Заказ может удалить его владелец или `ADMIN`.
10. При обращении обычного пользователя к чужому заказу сервис возвращает `404 Not Found`, как будто заказа не существует. Это не раскрывает наличие чужих данных.
11. Администратор не может удалить собственную учётную запись.

## 4. Модель данных

### 4.1. Таблица `users`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `UUID` | Первичный ключ, генерируется сервером |
| `username` | `VARCHAR(50)` | `NOT NULL`, `UNIQUE` |
| `password_hash` | `VARCHAR(60)` | `NOT NULL`, содержит BCrypt-хеш |
| `role` | `VARCHAR(20)` | `NOT NULL`, только `USER` или `ADMIN` |

В ТЗ поле названо `password`. В базе используется более точное имя `password_hash`, потому что исходный пароль не хранится.

### 4.2. Таблица `orders`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `UUID` | Первичный ключ, генерируется сервером |
| `user_id` | `UUID` | `NOT NULL`, внешний ключ на `users.id` |
| `description` | `VARCHAR(1000)` | `NOT NULL` |
| `status` | `VARCHAR(20)` | `NOT NULL`, один из допустимых статусов |
| `created_at` | `TIMESTAMP` | `NOT NULL`, устанавливается сервером |

Связь: один пользователь может иметь много заказов; каждый заказ принадлежит одному пользователю.

Внешний ключ `orders.user_id` использует `ON DELETE CASCADE`. При удалении пользователя база данных удаляет все его заказы.

Для ускорения выборки заказов пользователя предусматривается индекс по `orders.user_id`.

## 5. Статусы заказа

Допустимые значения:

- `CREATED`;
- `IN_PROGRESS`;
- `COMPLETED`.

Новый заказ всегда получает статус `CREATED`. Клиент не передаёт начальный статус.

В первой версии сложные правила переходов не вводятся: администратор может установить любое значение из списка. Неизвестное значение возвращает `400 Bad Request`.

## 6. API

Базовый префикс всех endpoint'ов: `/api`.

Для защищённых запросов JWT передаётся в заголовке:

```http
Authorization: Bearer <token>
```

### 6.1. Регистрация

```http
POST /api/auth/register
```

Доступ: публичный.

Запрос:

```json
{
  "username": "user_1",
  "password": "strong-password"
}
```

Успешный ответ: `201 Created`.

```json
{
  "id": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
  "username": "user_1",
  "role": "USER"
}
```

Ошибки:

- `400 Bad Request` — данные не прошли валидацию;
- `409 Conflict` — username уже занят.

### 6.2. Вход

```http
POST /api/auth/login
```

Доступ: публичный.

Запрос:

```json
{
  "username": "user_1",
  "password": "strong-password"
}
```

Успешный ответ: `200 OK`.

```json
{
  "token": "<jwt>",
  "tokenType": "Bearer",
  "expiresIn": 1800
}
```

Ошибка `401 Unauthorized` возвращается при неправильном username или пароле. Ответ не уточняет, какое именно поле было неверным.

### 6.3. Текущий пользователь

```http
GET /api/auth/me
```

Доступ: `USER`, `ADMIN`.

Успешный ответ: `200 OK`.

```json
{
  "id": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
  "username": "user_1",
  "role": "USER"
}
```

### 6.4. Список пользователей

```http
GET /api/users
```

Доступ: только `ADMIN`.

Успешный ответ: `200 OK`.

```json
[
  {
    "id": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
    "username": "user_1",
    "role": "USER"
  }
]
```

### 6.5. Удаление пользователя

```http
DELETE /api/users/{id}
```

Доступ: только `ADMIN`.

Успешный ответ: `204 No Content`.

Правила:

- вместе с пользователем каскадно удаляются его заказы;
- отсутствующий пользователь даёт `404 Not Found`;
- попытка администратора удалить самого себя даёт `409 Conflict`.

### 6.6. Создание заказа

```http
POST /api/orders
```

Доступ: `USER`, `ADMIN`.

Запрос:

```json
{
  "description": "Новый заказ"
}
```

Сервер самостоятельно устанавливает:

- `id`;
- владельца из текущей аутентификации;
- статус `CREATED`;
- дату создания.

Успешный ответ: `201 Created`.

```json
{
  "id": "2715fc32-0bc4-435d-ad2d-d09a7f19c607",
  "userId": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
  "description": "Новый заказ",
  "status": "CREATED",
  "createdAt": "2026-09-03T10:30:00"
}
```

### 6.7. Список заказов текущего пользователя

```http
GET /api/orders?page=0&size=20
```

Доступ: `USER`, `ADMIN`.

Возвращаются только заказы пользователя, которому принадлежит JWT. Передать чужой `userId` нельзя.

Успешный ответ: `200 OK`.

```json
{
  "content": [
    {
      "id": "2715fc32-0bc4-435d-ad2d-d09a7f19c607",
      "userId": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
      "description": "Новый заказ",
      "status": "CREATED",
      "createdAt": "2026-09-03T10:30:00"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

### 6.8. Список всех заказов

```http
GET /api/orders/all?page=0&size=20
```

Доступ: только `ADMIN`.

Формат ответа совпадает с пагинированным ответом `/api/orders`, но содержит заказы всех пользователей.

### 6.9. Изменение статуса заказа

```http
PUT /api/orders/{id}
```

Доступ: только `ADMIN`.

Запрос:

```json
{
  "status": "IN_PROGRESS"
}
```

Успешный ответ: `200 OK` с актуальным представлением заказа.

Ошибки:

- `400 Bad Request` — статус отсутствует или неизвестен;
- `404 Not Found` — заказ не найден.

Описание, владелец и дата создания этим endpoint'ом не изменяются.

### 6.10. Удаление заказа

```http
DELETE /api/orders/{id}
```

Доступ: владелец заказа или `ADMIN`.

Успешный ответ: `204 No Content`.

Правила:

- `ADMIN` может удалить любой существующий заказ;
- `USER` удаляет заказ только при совпадении владельца с текущим пользователем;
- для `USER` чужой и несуществующий заказ дают одинаковый ответ `404 Not Found`;
- это правило не позволяет подтвердить существование чужого заказа по его UUID.

Endpoint `GET /api/orders/{id}` не добавляется, потому что его нет в ТЗ.

## 7. Пагинация

Пагинация применяется к обоим спискам заказов.

| Параметр | Значение по умолчанию | Ограничение |
|---|---:|---:|
| `page` | `0` | Не меньше `0` |
| `size` | `20` | От `1` до `100` |

Сортировка по умолчанию: `createdAt` по убыванию, сначала новые заказы.

Неверные параметры пагинации возвращают `400 Bad Request`.

## 8. Валидация

### 8.1. Username

- обязательное поле;
- от 3 до 50 символов;
- разрешены латинские буквы, цифры и `_`;
- пробелы запрещены;
- перед сохранением приводится к нижнему регистру;
- уникальность проверяется по нормализованному значению.

Ограничение приложения соответствует `VARCHAR(50)` в базе.

### 8.2. Password

- обязательное поле;
- не менее 8 Unicode code points (обычных Unicode-символов);
- не более 72 байт после кодирования строки в UTF-8;
- пароль длиннее лимита BCrypt отклоняется и никогда не обрезается;
- проверяется только во входном DTO;
- исходный пароль не сохраняется.

База хранит BCrypt-хеш длиной 60 символов в `VARCHAR(60)`.

### 8.3. Description

- обязательное поле;
- строка только из пробелов запрещена;
- после удаления пробелов по краям — от 1 до 1000 символов.

Ограничение приложения соответствует `VARCHAR(1000)` в базе.

## 9. Пароли и создание администратора

Пароли хешируются с помощью `BCryptPasswordEncoder`. Проверка выполняется через `matches()`. Хеш и исходный пароль никогда не возвращаются клиенту и не записываются в логи.

Первый администратор создаётся при запуске приложения специальным инициализатором, если администратора ещё нет. Данные передаются через переменные окружения:

```text
ADMIN_USERNAME
ADMIN_PASSWORD
```

Пароль немедленно преобразуется в BCrypt-хеш. Повторный запуск приложения не перезаписывает существующего администратора. Автоматическую инициализацию можно отключить в тестах.

## 10. JWT

| Параметр | Решение |
|---|---|
| Алгоритм | `HS256` |
| Срок действия | 30 минут / 1800 секунд |
| Refresh token | Не используется |
| Секрет | Переменная окружения `JWT_SECRET` |
| Минимальный размер секрета | 32 байта |
| Поле `sub` | Username |

При каждом защищённом запросе приложение:

1. Извлекает JWT из заголовка `Authorization`.
2. Проверяет подпись и срок действия.
3. Получает username из `sub`.
4. Загружает актуального пользователя из базы.
5. Создаёт аутентификацию Spring Security.

Поэтому JWT удалённого пользователя больше не работает: пользователь не будет найден в базе.

## 11. Единый формат ошибок

Обычная ошибка:

```json
{
  "timestamp": "2026-09-03T10:30:00",
  "status": 404,
  "error": "Not Found",
  "message": "Пользователь не найден",
  "path": "/api/users/15"
}
```

Ошибка валидации дополнительно содержит `fieldErrors`:

```json
{
  "timestamp": "2026-09-03T10:30:00",
  "status": 400,
  "error": "Bad Request",
  "message": "Ошибка валидации",
  "path": "/api/auth/register",
  "fieldErrors": [
    {
      "field": "username",
      "message": "Username должен содержать от 3 до 50 символов"
    }
  ]
}
```

Основные HTTP-статусы:

| Статус | Значение в сервисе |
|---:|---|
| `400` | Ошибка валидации, неизвестный статус или неверная пагинация |
| `401` | JWT отсутствует/недействителен либо неверны данные для входа |
| `403` | Пользователь аутентифицирован, но endpoint недоступен его роли |
| `404` | Объект не найден либо пользователь пытается обратиться к чужому заказу |
| `409` | Username занят или администратор пытается удалить себя |
| `500` | Неожиданная внутренняя ошибка |

Разница между `403` и `404`:

- `USER`, вызывающий административный endpoint `/api/orders/all`, получает `403`, потому что запрет относится ко всему endpoint'у;
- `USER`, пытающийся удалить чужой заказ по UUID, получает `404`, чтобы сервис не раскрывал существование конкретного заказа.

## 12. Что не входит в первую версию

- получение одного заказа через `GET /api/orders/{id}`;
- редактирование описания заказа;
- назначение роли при публичной регистрации;
- refresh-токены;
- восстановление пароля;
- мягкое удаление пользователей;
- сложные правила перехода статусов;
- отдельный frontend.
