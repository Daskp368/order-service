# Этап 13. Пагинация заказов

## Результат

Оба списка заказов возвращаются страницами:

```http
GET /api/orders?page=0&size=20
GET /api/orders/all?page=0&size=20
Authorization: Bearer <token>
```

`GET /api/orders` содержит только заказы владельца JWT. `GET /api/orders/all` по-прежнему доступен
только `ADMIN` и содержит заказы всех пользователей. Пагинация не изменила правила безопасности и
владения данными.

## Контракт параметров

| Параметр | Значение по умолчанию | Допустимые значения |
|---|---:|---:|
| `page` | `0` | `0` и больше |
| `size` | `20` | от `1` до `100` |

Номер страницы начинается с нуля. Поэтому при `size=3`:

- `page=0` содержит записи 1–3;
- `page=1` содержит записи 4–6;
- `page=2` содержит записи 7–9.

Запрос без параметров равнозначен следующему:

```http
GET /api/orders?page=0&size=20
```

Параметр `sort` на этапе 13 не открыт клиенту. Дорожная карта делает его необязательным, а
согласованный контракт фиксирует серверную сортировку заказов от новых к старым.

## Формат успешного ответа

```json
{
  "content": [
    {
      "id": "2715fc32-0bc4-435d-ad2d-d09a7f19c607",
      "userId": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
      "description": "Новый заказ",
      "status": "CREATED",
      "createdAt": "2026-09-15T10:30:00"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

Поля ответа:

- `content` — заказы текущей страницы;
- `page` — фактически запрошенный номер страницы;
- `size` — запрошенный максимальный размер страницы;
- `totalElements` — количество всех подходящих заказов без ограничения одной страницей;
- `totalPages` — количество страниц при текущем `size`.

Если запрошенная страница находится после последней, сервер возвращает `200 OK`, пустой `content` и
корректные общие метаданные. Это допустимая пустая выборка, а не ошибка клиента.

## Почему используется собственный PagedResponse

Сервис не возвращает объект Spring `Page` прямо из контроллера. Внешний API использует отдельный
`PagedResponse<T>` ровно с пятью согласованными полями.

Это даёт следующие свойства:

- JSON не зависит от внутренних деталей сериализации Spring Data;
- клиент не получает лишние служебные поля сортировки и `Pageable`;
- контракт можно изменять осознанно, не меняя слой репозитория;
- один DTO можно повторно использовать для разных типов содержимого.

Параметр типа `<T>` означает, что `PagedResponse` не привязан к заказу. В этом этапе вместо `T`
используется `OrderResponse`, поэтому фактический тип ответа — `PagedResponse<OrderResponse>`.

Конструктор применяет `List.copyOf(content)`. После создания DTO его список нельзя изменить через
ссылку, переданную вызывающему коду.

## RequestParam и query-параметры

Методы контроллера принимают параметры так:

```java
@RequestParam(defaultValue = "0") int page,
@RequestParam(defaultValue = "20") int size
```

`@RequestParam` обрабатывает Spring MVC. Аннотация связывает значение после `?` в URL с аргументом
Java-метода и применяет преобразование строки в `int`.

Если параметр отсутствует, используется `defaultValue`. Если передана строка, которую невозможно
преобразовать в число, Spring выбрасывает `MethodArgumentTypeMismatchException`. Уже существующий
`ApiExceptionHandler` возвращает для неё единый `400 Bad Request`.

Без явных `defaultValue` клиент должен был бы обязательно передавать оба значения либо контроллеру
потребовалась бы другая логика обработки отсутствующих параметров.

## Проверка границ страницы

`OrderService.createPageable` проверяет бизнес-ограничения перед обращением к репозиторию:

```text
page < 0             → 400 Bad Request
size < 1             → 400 Bad Request
size > 100           → 400 Bad Request
```

Неверное значение приводит к `InvalidPaginationException`. Обработчик с `@ExceptionHandler` переводит
его в уже принятый формат ошибки:

```json
{
  "timestamp": "2026-09-15T10:30:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Параметр size должен быть от 1 до 100",
  "path": "/api/orders"
}
```

Сервис отклоняет слишком большой `size`, а не молча уменьшает его до `100`. Клиент сразу узнаёт, что
нарушил контракт. Ограничение не позволяет одним запросом загрузить в память приложение и передать по
сети всю таблицу заказов.

`@ExceptionHandler(InvalidPaginationException.class)` обрабатывает Spring MVC через
`ApiExceptionHandler`. Без этого метода исключение дошло бы до общего обработчика и выглядело бы как
`500 Internal Server Error`, хотя ошибка находится в параметрах клиента.

## Pageable, PageRequest и Page

### Pageable

`Pageable` — интерфейс, описывающий запрос страницы:

- номер страницы;
- размер страницы;
- сортировку.

Он не содержит найденные заказы. Это только инструкция для репозитория.

### PageRequest

`PageRequest` — готовая реализация `Pageable`. Сервис создаёт её после проверки параметров:

```java
PageRequest.of(page, size, DEFAULT_ORDER_SORT)
```

### Page

`Page<Order>` — результат выполнения запроса. В нём находятся:

- сущности текущей страницы;
- номер и размер страницы;
- общее число подходящих записей;
- вычисленное число страниц.

Метод `Page.map(this::toResponse)` преобразует каждую сущность `Order` в безопасный `OrderResponse`,
сохраняя метаданные страницы.

## Репозиторий

Выборка заказов владельца объявлена так:

```java
Page<Order> findAllByUser_Id(UUID userId, Pageable pageable);
```

Spring Data разбирает имя метода и добавляет условие по `Order.user.id`. Пагинацию и сортировку он
получает из `Pageable`.

Для списка всех заказов отдельный derived query больше не нужен. `JpaRepository` уже предоставляет:

```java
Page<Order> findAll(Pageable pageable);
```

В обоих случаях ограничение страницы выполняется PostgreSQL. Приложение не загружает всю таблицу и не
отрезает нужный участок списка в Java.

## Стабильная сортировка

Основная сортировка:

```text
createdAt DESC
```

Если два заказа созданы в одну и ту же долю секунды, их `createdAt` совпадает. Без второго критерия база
не обязана каждый раз возвращать такие строки в одинаковом взаимном порядке. Это может привести к
повторению или пропуску записи на границе страниц.

Поэтому полный порядок задаётся так:

```text
createdAt DESC, id DESC
```

UUID заказа уникален, поэтому сочетание двух полей однозначно определяет место каждой записи в
неизменном наборе данных.

Обычная offset-пагинация не фиксирует снимок таблицы. Если между двумя HTTP-запросами добавить или
удалить заказ, состав последующих страниц может сдвинуться. Для учебного контракта достаточно
стабильного порядка в неизменном наборе; cursor-пагинация в этап 13 не входит.

## Что выполняет PostgreSQL

Для `Page` Spring Data обычно выполняет два запроса:

1. Запрос содержимого с фильтрацией, `ORDER BY`, смещением и ограничением количества строк.
2. Запрос `COUNT`, чтобы вычислить `totalElements` и `totalPages`.

Упрощённый смысл личной страницы:

```sql
SELECT ...
FROM orders
WHERE user_id = ?
ORDER BY created_at DESC, id DESC
OFFSET ? ROWS
FETCH FIRST ? ROWS ONLY;
```

Упрощённый смысл подсчёта:

```sql
SELECT COUNT(*)
FROM orders
WHERE user_id = ?;
```

`offset` рассчитывается из номера и размера страницы:

```text
offset = page × size
```

Например, для `page=2&size=5` база пропускает первые 10 подходящих записей.

## Путь запроса

```text
GET /api/orders?page=1&size=2 + Bearer JWT
          ↓
JwtAuthenticationFilter проверяет токен и создаёт Authentication
          ↓
Spring MVC преобразует page и size из строк URL в int
          ↓
OrderController передаёт username, page и size в OrderService
          ↓
OrderService проверяет границы и создаёт PageRequest
          ↓
UserRepository находит актуального владельца по username
          ↓
OrderRepository получает Page<Order> только этого владельца
          ↓
Page.map преобразует Order Entity в OrderResponse
          ↓
PagedResponse<OrderResponse> → JSON → 200 OK
```

Для `/api/orders/all` Spring Security сначала проверяет `ROLE_ADMIN`, после чего сервис вызывает
унаследованный `findAll(Pageable)`. Обычный `USER` получает `403` до вызова контроллера.

## Транзакционная граница

Оба метода списка остаются под `@Transactional(readOnly = true)`. Аннотацию обрабатывает транзакционный
proxy Spring.

Транзакция охватывает получение `Page<Order>` и преобразование сущностей в DTO. Это важно, потому что
`Order.user` загружается лениво, а `toResponse` читает `order.getUser().getId()`.

## Проверенные сценарии

`OrderPaginationIntegrationTest` проверяет:

- явные `page` и `size`;
- значения по умолчанию `0` и `20`;
- точные поля метаданных;
- отсутствие заказов другого пользователя;
- разные непересекающиеся страницы;
- общий список ADMIN;
- стабильный порядок при одинаковом `createdAt`;
- пустой `content` после последней страницы;
- `400` для `page=-1`, `size=0` и `size=101`;
- `400` для нечислового `size`.

Результаты после реализации:

- целевой запуск — 23 теста, 0 ошибок и 0 падений;
- полный `./mvnw test` — 73 теста, 0 ошибок и 0 падений.

## Граница этапа

На этапе 13 не добавлялись:

- клиентская сортировка через параметр `sort`;
- пагинация списка пользователей;
- cursor-пагинация;
- новая миграция или индекс;
- Swagger / OpenAPI;
- Docker;
- получение заказа по ID;
- редактирование описания заказа.

Swagger относится к этапу 14, а расширение набора unit- и интеграционных тестов — к этапу 15.

6. Откуда берутся `totalElements` и `totalPages`?
