# Этап 12. Удаление заказов и пользователей

## Результат

Реализованы два защищённых endpoint:

```http
DELETE /api/orders/{id}
DELETE /api/users/{id}
Authorization: Bearer <token>
```

Владелец может удалить собственный заказ, а ADMIN — любой заказ. Удалять пользователей может только
ADMIN, при этом администратору запрещено удалять собственную учётную запись. При удалении пользователя
PostgreSQL каскадно удаляет все принадлежащие ему заказы.

Успешное удаление возвращает `204 No Content`: операция выполнена, но представление уже удалённого ресурса
в ответе не требуется.

## Матрица доступа

| Endpoint и ситуация | anonymous | USER | ADMIN |
|---|---:|---:|---:|
| `DELETE /api/orders/{id}`, собственный заказ | `401` | `204` | `204` |
| `DELETE /api/orders/{id}`, чужой заказ | `401` | `404` | `204` |
| `DELETE /api/orders/{id}`, заказ отсутствует | `401` | `404` | `404` |
| `DELETE /api/users/{id}`, другой пользователь | `401` | `403` | `204` |
| `DELETE /api/users/{id}`, пользователь отсутствует | `401` | `403` | `404` |
| `DELETE /api/users/{id}`, ADMIN удаляет себя | `401` | — | `409` |

`401 Unauthorized` означает, что подтверждённой аутентификации нет. `403 Forbidden` означает, что JWT
подтверждён, но роль не разрешает обращаться к административному endpoint. `404 Not Found` используется,
когда ресурс отсутствует, а также когда USER передал UUID чужого заказа. `409 Conflict` сообщает, что
пользователь существует, но операция конфликтует с правилом запрета самоудаления администратора.

## Удаление заказа владельцем

Запрос:

```http
DELETE /api/orders/2715fc32-0bc4-435d-ad2d-d09a7f19c607
Authorization: Bearer <user-token>
```

Контроллер получает UUID из пути и username из текущей `Authentication`:

```java
@DeleteMapping("/{id}")
public ResponseEntity<Void> deleteOrder(@PathVariable UUID id, Authentication authentication) {
    orderService.deleteOrder(id, authentication.getName());
    return ResponseEntity.noContent().build();
}
```

Клиент не передаёт владельца в query-параметре или JSON. Источник истины — пользователь, чья
аутентификация создана JWT-фильтром.

Для обычного пользователя сервис выполняет запрос, в котором одновременно участвуют два условия:

```java
findByIdAndUser_Id(orderId, currentUser.getId())
```

Смысл derived query:

```sql
SELECT ...
FROM orders
WHERE id = :orderId
  AND user_id = :currentUserId;
```

Если заказ существует, но принадлежит другому пользователю, запрос не возвращает строку. Результат
совпадает с результатом поиска отсутствующего UUID — `ResourceNotFoundException` и `404 Not Found`.
Так API не подтверждает существование чужого заказа.

Путь успешного запроса владельца:

```text
DELETE /api/orders/{id} + Bearer JWT
          ↓
JwtAuthenticationFilter проверяет токен
          ↓
DatabaseUserDetailsService загружает актуального пользователя
          ↓
SecurityFilterChain требует аутентификацию
          ↓
OrderController.deleteOrder(...)
          ↓
OrderService.deleteOrder(...)
          ↓
UserRepository.findByUsername(...)
          ↓
OrderRepository.findByIdAndUser_Id(orderId, userId)
          ↓
OrderRepository.delete(order)
          ↓
SQL DELETE FROM orders WHERE id = ?
          ↓
204 No Content
```

## Удаление заказа администратором

Для ADMIN действует тот же HTTP endpoint. Различие находится в бизнес-логике сервиса:

```java
if (currentUser.getRole() == Role.ADMIN) {
    return orderRepository.findById(orderId)
            .orElseThrow(() -> new ResourceNotFoundException("Заказ не найден"));
}
```

ADMIN ищет заказ только по UUID, поэтому владелец не ограничивает операцию. Отдельный административный
DELETE-маршрут не нужен: роль и владелец учитываются внутри одной бизнес-операции.

`SecurityConfig` не ограничивает этот endpoint через `hasRole("ADMIN")`. Общее правило
`.anyRequest().authenticated()` пропускает USER и ADMIN, а сервис принимает решение для конкретного
ресурса.

## Удаление пользователя

Запрос:

```http
DELETE /api/users/0dbdfd3c-439c-46ab-ab78-a7cbe86d540f
Authorization: Bearer <admin-token>
```

`DELETE /api/users/{id}` полностью административный, поэтому `SecurityFilterChain` проверяет
`hasRole("ADMIN")` до вызова контроллера. USER получает `403 Forbidden`, и `UserController` с
`UserService` вообще не выполняются.

В сервисе происходят следующие действия:

1. По username из `Authentication` загружается текущий администратор.
2. По UUID из пути загружается удаляемый пользователь.
3. Идентификаторы сравниваются для проверки самоудаления.
4. При совпадении выбрасывается `SelfDeletionNotAllowedException`.
5. В остальных случаях `UserRepository.delete(userToDelete)` помечает сущность для удаления.
6. Hibernate выполняет `DELETE FROM users WHERE id = ?` при синхронизации транзакции с базой.

Если пользователь отсутствует, сервис выбрасывает `ResourceNotFoundException("Пользователь не найден")`
и клиент получает `404 Not Found`.

## Почему самоудаление даёт 409

Текущий ADMIN имеет право обращаться к endpoint, поэтому `401` и `403` здесь неверны. Целевой пользователь
тоже существует, поэтому это не `404`. Операция запрещена отдельным правилом согласованного API-контракта:
администратор не может удалить собственную учётную запись.

`SelfDeletionNotAllowedException` выражает это правило без зависимости сервисного слоя от HTTP.
`ApiExceptionHandler` преобразует исключение в ответ:

```json
{
  "timestamp": "2026-09-14T13:53:18Z",
  "status": 409,
  "error": "Conflict",
  "message": "Администратор не может удалить собственную учётную запись",
  "path": "/api/users/0dbdfd3c-439c-46ab-ab78-a7cbe86d540f"
}
```

## Каскадное удаление заказов пользователя

Связь уже определена в `V1__create_users_and_orders.sql`:

```sql
CONSTRAINT fk_orders_user
    FOREIGN KEY (user_id)
    REFERENCES users (id)
    ON DELETE CASCADE
```

При удалении строки `users` PostgreSQL сам удаляет строки `orders`, которые ссылаются на неё. Это
поддерживает ссылочную целостность: в таблице заказов не остаются записи с отсутствующим владельцем.

В `User` по-прежнему нет `List<Order>` и JPA-настройки `cascade = REMOVE`. Для текущей модели они не нужны:
связь в Java односторонняя, а политика удаления принадлежит схеме базы. Уже применённая миграция V1 не
изменялась.

## Транзакционная граница

Оба сервисных метода удаления помечены `@Transactional`:

```java
@Transactional
public void deleteOrder(...)

@Transactional
public void deleteUser(...)
```

Поиск, проверка правил и удаление выполняются как одна бизнес-операция. Если после проверки возникает
исключение, транзакция откатывается. SQL удаления обычно выполняется при flush или commit, когда Hibernate
синхронизирует persistence context с PostgreSQL.

Для `204 No Content` не создаётся DTO. Тип `ResponseEntity<Void>` показывает, что ответ не содержит
представления ресурса.

## Что происходит с JWT удалённого пользователя

JWT содержит username, но при каждом защищённом запросе `DatabaseUserDetailsService` повторно загружает
актуального пользователя из PostgreSQL. После удаления запись больше не находится, а JWT-фильтр не
создаёт `Authentication`.

Следующий защищённый запрос со старым токеном получает `401 Unauthorized`. Отдельный список отозванных
токенов для этого поведения не требуется.

## Новые аннотации и механизмы

### `@DeleteMapping("/{id}")`

Регистрирует метод Spring MVC для HTTP DELETE. Без аннотации маршрут не существует и контроллер не будет
вызван.

### `@PathVariable`

Связывает сегмент `{id}` с параметром `UUID`. Если строка не является UUID, преобразование завершается
до сервиса, а `ApiExceptionHandler` возвращает `400 Bad Request`.

### `@Transactional`

Создаёт транзакционную границу вокруг поиска, проверки и удаления. Без неё отдельные обращения к
репозиторию не образуют одну атомарную бизнес-операцию.

### `ResponseEntity<Void>`

Описывает HTTP-ответ без тела. `ResponseEntity.noContent().build()` устанавливает статус `204`.

### Derived query с вложенным свойством

Имя `findByIdAndUser_Id` читается Spring Data как поиск по `Order.id` и вложенному `Order.user.id`.
Реализацию интерфейса и SQL Spring Data создаёт автоматически.

## Проверки

`DeletionOperationsIntegrationTest` проходит настоящий путь Security → Controller → Service → Repository →
PostgreSQL и проверяет:

- удаление собственного заказа владельцем;
- удаление любого заказа администратором;
- одинаковый `404` для чужого и отсутствующего заказа у USER;
- сохранность заказа после запрещённой попытки;
- `400` для некорректного UUID заказа и пользователя;
- каскадное удаление заказов вместе с пользователем;
- `403` для USER при удалении пользователя;
- `409` и сохранность учётной записи при самоудалении ADMIN;
- `401` без JWT;
- отказ старого JWT после удаления его владельца.

Результаты после реализации:

- `./mvnw -Dtest=DeletionOperationsIntegrationTest test` — 9 тестов, 0 ошибок и 0 падений;
- `./mvnw test` — 64 теста, 0 ошибок и 0 падений.
