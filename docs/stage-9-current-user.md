# Этап 9. Текущий пользователь

## Результат

Реализован защищённый endpoint:

```http
GET /api/auth/me
Authorization: Bearer <token>
```

Он определяет пользователя по текущей аутентификации, загружает его актуальные данные из PostgreSQL и возвращает безопасный профиль без пароля и BCrypt-хеша.

## Контракт endpoint

Запрос не содержит тела, `userId` или username. Единственным подтверждением личности является Bearer-токен:

```http
GET /api/auth/me
Authorization: Bearer eyJ...
```

Успешный ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "id": "0dbdfd3c-439c-46ab-ab78-a7cbe86d540f",
  "username": "user_1",
  "role": "USER"
}
```

Без токена, с недействительным токеном или с токеном удалённого пользователя запрос получает единый `401 Unauthorized`, настроенный на этапе 8.

## Путь запроса

```text
GET /api/auth/me + Authorization: Bearer <token>
          ↓
SecurityFilterChain
          ↓
JwtAuthenticationFilter
          ↓
JwtService проверяет структуру, подпись HS256 и exp
          ↓
DatabaseUserDetailsService загружает пользователя из PostgreSQL
          ↓
Authentication помещается в SecurityContext
          ↓
AuthController получает текущую Authentication
          ↓
AuthController передаёт authentication.getName() в AuthService
          ↓
UserRepository.findByUsername(username)
          ↓
UserResponse(id, username, role) → 200 OK
```

До контроллера доходят только запросы, для которых Spring Security создал подтверждённую `Authentication`.

## Текущая `Authentication`

Метод контроллера объявляет параметр типа `Authentication`:

```java
public ResponseEntity<UserResponse> currentUser(Authentication authentication)
```

Этот параметр не создаётся из JSON и не передаётся клиентом. Spring MVC получает его из `SecurityContext`, заполненного JWT-фильтром для текущего запроса.

`Authentication` одновременно описывает:

- principal — подтверждённого пользователя;
- authorities — его текущие полномочия;
- состояние аутентификации;
- имя пользователя, доступное через `getName()`.

Интерфейс `Authentication` расширяет `Principal`, поэтому `authentication.getName()` является именем текущего principal.

## Почему профиль снова читается из базы

JWT этапа 8 содержит только стандартные claims `sub`, `iat` и `exp`. В `sub` записан username, но в токене нет UUID и роли.

После проверки JWT фильтр загружает пользователя и создаёт стандартный Spring Security `UserDetails`. Такой principal содержит username, BCrypt-хеш и authorities, но не является доменной JPA-сущностью `User` и не содержит UUID.

Для ответа `/me` сервис поэтому выполняет отдельный поиск доменного пользователя:

```java
userRepository.findByUsername(username)
```

Из найденной сущности в `UserResponse` переносятся только разрешённые поля. Entity напрямую из контроллера не возвращается.

Так сохраняется граница:

- JWT подтверждает, от чьего имени выполняется запрос;
- база данных остаётся источником актуальных данных профиля;
- DTO определяет, какие данные разрешено показать клиенту.

## Почему нельзя принимать `userId`

Если бы `/me` принимал `userId`, клиент мог бы заменить его идентификатором другого пользователя. Проверенный JWT при этом принадлежал бы одному человеку, а запрошенный профиль — другому.

Endpoint не объявляет `@RequestParam`, `@PathVariable` или поле DTO для идентификатора пользователя. Даже если клиент добавит `?userId=<чужой-id>`, сервис его не использует и возвращает владельца JWT.

Этот же принцип понадобится на следующем этапе: владелец создаваемого заказа будет определяться сервером, а не приниматься из запроса.

## Новые аннотации и механизмы

### `@GetMapping("/me")`

Регистрирует метод контроллера для HTTP-запроса `GET /api/auth/me`. Без этой аннотации Spring MVC не свяжет URL с Java-методом.

### `@Transactional(readOnly = true)`

Открывает транзакционную границу для чтения доменного пользователя. `readOnly = true` сообщает, что метод не должен изменять данные.

### Внедрение `Authentication` в аргумент метода

Это не аннотация. Spring MVC умеет передавать текущую `Authentication` как специальный аргумент метода контроллера. Значение берётся из `SecurityContextHolder`, а не из пользовательского ввода.

## Тесты

`AuthMeIntegrationTest` проверяет полный путь через Spring Security, контроллер, сервис, репозиторий и PostgreSQL:

- токен `USER` возвращает профиль этого пользователя;
- токен `ADMIN` возвращает профиль администратора;
- токены двух пользователей возвращают разные `id`, username и роли;
- переданный query-параметр `userId` не позволяет выбрать чужой профиль;
- JSON содержит ровно `id`, `username` и `role`;
- поля `password` и `passwordHash` отсутствуют;
- запрос без токена получает единый `401 Unauthorized`.

Проверка после реализации:

- целевой запуск `./mvnw -Dtest=AuthMeIntegrationTest test` — 2 теста, 0 ошибок;
- полный запуск `./mvnw test` — 38 тестов, 0 ошибок.
